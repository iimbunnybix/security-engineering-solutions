# 010 · A customer downloaded the server's database password through the "download your export" link

## Problem
A B2B analytics product lets each customer download their generated exports
from `GET /exports/download?file=2026/orders-10.csv`. Files live under
`/srv/app/exports/<tenant>/`. A security researcher reported that
`?file=../../config/app.env` returned the application's environment file,
including the production database password, and that
`?file=../globex/2026/orders-10.csv` returned another customer's export. The
team rotated every credential in that file and had to review months of access
logs to work out which tenants' exports had been read by someone else.

## Root cause
**Path traversal (CWE-22).** The handler built the path with
`os.path.join(tenant_dir, unquote(file))` and opened it:

- `..` segments walk out of the tenant directory, into another tenant or the
  app's config;
- an **absolute** name (`/srv/app/config/app.env`) makes `os.path.join`
  discard the base directory entirely;
- the extra `unquote` meant a **double-encoded** payload (`%252e%252e%252f`)
  got past any check done on the once-decoded value;
- a **symlink** inside the export directory (created by a buggy export job or
  extracted from an uploaded archive) points anywhere;
- a **hard link** in the export directory is the target file itself under a
  second name: there is no link target to resolve, so a path check alone
  cannot tell it apart from a real export.

A first hot-fix removed `../` with `str.replace`. `....//` becomes `../`
after that single pass, so it was bypassed the same day. Every one of these
attacks is reproduced in the tests against the original handler (and the
blocklist bypass against the hot-fix), reading the fake secret or the other
tenant's file.

## Solution
`safe_resolve` / `handle_download` in `solution.py`:

1. **Validate the name before touching the filesystem:** length 1–255, no
   NUL or backslash, not absolute, no empty, `.` or `..` segments. **No extra
   decoding**: the framework decodes the query string once and that is final.
2. **Resolve, then check containment.** The tenant root and the target are
   resolved with `Path.resolve(strict=True)` (following symlinks), and the
   target must satisfy `target.is_relative_to(root)` and be a regular file.
   Checking the *resolved* path is what catches symlinks and anything the
   validation step missed.
3. **The tenant comes from the session**, not the URL, and must be
   alphanumeric, so it cannot traverse either.
4. **Open with `O_NOFOLLOW`** where supported, then `fstat` the opened fd:
   it must be a regular file with `st_nlink == 1`. Export files are written
   by the app and never hard-linked, so a second link means the name is an
   alias of some other file (e.g. `config/app.env`). Return the same
   **404 "not found"** for every rejection so the endpoint does not reveal
   which paths exist.

Twelve attack strings (traversal, absolute, encoded, blocklist bypass,
backslashes, NUL, cross-tenant, oversized) all return 404. Legitimate nested
files and symlinks that stay *inside* the tenant directory still work.

## Trade-offs
- **Best option: don't accept paths at all.** Store exports in a table and
  download by opaque id (`/exports/7f3c…`) after an ownership check; the
  filesystem path never comes from the client. This code is for systems that
  must serve by name.
- There is a small race (TOCTOU) between resolving and opening: a symlink
  swapped in between could still be followed in a parent directory.
  `O_NOFOLLOW` covers the final component; for full protection, open
  relative to a directory fd (`openat2` with `RESOLVE_BENEATH` on Linux)
  or ensure only the app can write to the export tree.
- Rejecting `\` and dot segments may block odd but legitimate names; export
  names are generated by the app, so a strict format is acceptable here.
- The `st_nlink == 1` rule would reject legitimate hard links (e.g. a
  deduplicating backup tool); if you need those, compare `st_dev`/`st_ino`
  against an inventory of files the app wrote instead. Extract uploaded
  archives with `tarfile`'s `filter="data"`, which refuses links that
  point outside the destination.
- Run the service as a user that cannot read `config/` at all (secrets via
  a secret manager or env injection), so a future traversal finds less.
